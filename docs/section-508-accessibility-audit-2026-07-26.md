# ResumeMatch — Accessibility Conformance Report (Section 508 / WCAG 2.1 AA)

**Product:** ResumeMatch web application — https://resumematchapp.com
**Scope:** Frontend (React 18 SPA): landing page, authentication, resume upload & analysis, sample report, application tracker
**Not audited:** the mock interview flow (`/interview`, `/interview/history`, `/interview/results/:sessionId`), the dashboard (`/dashboard`), analysis history (`/history`), the signed-in analysis detail page (`/results/:analysisId`), and the remaining auth and legal pages (`/signup`, `/forgot-password`, `/privacy`, `/terms`).
**Audit date:** 2026-07-26
**Method:** Automated audit (Lighthouse 13.4.1, accessibility category only, **mobile** form factor, 412x823 at DPR 1.75) + manual keyboard walkthrough + source-level code review
**Test target:** the production build served locally by `vite preview` at `http://localhost:4173`, not the deployed site at the URL above. No desktop form factor was run.
**Standard applied:** WCAG 2.1 Level AA (the standard incorporated by the revised Section 508)

## Summary

**All five representative pages score 100/100 in both themes** on the Lighthouse accessibility audit. Dark has held 100 since 2026-07-26, measured against the tree committed as `58fe0a0` and confirmed again at HEAD on 2026-07-27. Light reached 100 on 2026-07-27.

**Light did not pass before that date, and the failure is kept on record rather than removed.** Until 2026-07-27, three of the five routes failed `color-contrast` in light: the landing page scored 97 (25 failing elements), sign-in 95 (3) and the sample report 95 (16). It was long-standing rather than new, it reproduced on `58fe0a0`, and it stayed invisible because every archived run before 2026-07-27 was captured in the dark theme. It was not a secondary path either: the app resolves an unset theme preference from `prefers-color-scheme`, so a first-time visitor on a light-mode OS gets the light theme. Five design tokens accounted for all 44 failing nodes: `--accent`, `--text-tertiary`, `--success`, `--success-alt` and `--warn`. All five were corrected on 2026-07-27. The measurements are in **1.4.3**, the changes in the **Remediation log (2026-07-27)**, and the before and after runs in the **Evidence archive**.

Automated checks are complemented by the manual verification listed below, since automated tooling covers only a subset of WCAG success criteria. Full Lighthouse reports (HTML + JSON) are archived alongside this document; see **Evidence archive** for what the archive does and does not cover.

## Manual checks performed (items automated tooling cannot cover)

Verified 2026-07-26 by keyboard walkthrough and code review:

- Interactive controls are keyboard focusable, and indicate purpose and state (ARIA labels and state attributes present).
- Tab order is logical; visual order follows DOM order (no `order:` or reverse-flex CSS in the codebase).
- Focus is never unintentionally trapped; modal traps release on Escape and return focus to the invoking element.

## Remediation log (2026-07-27)

Light-theme contrast. Every ratio below is measured. Unlike the 2026-07-26 entries, **this round has complete before-side evidence**: `docs/lighthouse-2026-07-27/light/` is the full pre-fix set and `light-postfix/` the full post-fix set, same settings, all five routes, both themes.

- `--brand-tint-text` (light) from `#5e6ad2` to `#4852b8`. This was the only tint-text member in the light palette never darkened from its base; success, warn and danger all were. It clears 4.5:1 on all four accent-tinted surfaces, worst case 5.22:1 on `#e1e4f2`. Its 33 call sites across 13 files pick the new value up with no call-site edits, which covers 27 of the 30 `--accent` nodes.
- `--link` (light) from `#5e6ad2` to `#515dc8`, 5.26:1 on `--surface-inset` `#f7f8f8`. Chosen to stay lighter than both `--link-hover` `#4c58c4` and `--accent-hover` `#4852b8`, so that every link hover still darkens instead of resolving to the same colour and going dead.
- A light-scoped anchor rule, `:where([data-theme="light"]) a`, added rather than repointing the global `a` rule. That rule is theme-agnostic, so repointing it would have restyled dark anchors from `#5e6ad2` to `#828fff` for no accessibility gain. Dark keeps `--accent`, and the `:root` and `[data-theme="dark"]` blocks are byte-identical to the previous commit, verified by block-level diff.
- `--text-tertiary` (light) from `#6c7482` to `#68707d`: 5.00:1 on `#ffffff`, 4.70:1 on `#f7f8f8`, 4.54:1 on the real floor `#f3f4f5`. The margin is constrained; see 1.4.3.
- Four call sites moved to the family member intended for light surfaces: `.landing-count--success` and `.results-diff-callout__count` from `--success-alt` to `--pill-success-text` (4.72:1 and 5.00:1); `.landing-session__match` from `--warn` to `--pill-warn-text` (5.04:1); and `.landing-tile__value--high` from `--score-high` to `--pill-success-text`, which is a knowing divergence from the real Results tiles and is recorded under Known issues.
- Two resting-surface repoints, a usage fix rather than a colour fix. `.outreach-queue__reason-pts--zero` and `.tracker-detail__chip-pts--zero` were using the hover token `--surface-card-hover` `#f3f4f5` as a resting background. Both now use `--surface-inset` `#f7f8f8`, which lifts them off the floor instead of tuning a colour to reach it: 4.28:1 to 4.70:1.

**A regression was introduced during this round and caught before the commit.** The light anchor rule was first written as `[data-theme="light"] a`, specificity (0,1,1), which beats `.btn` at (0,1,0) and repainted anchor-styled button labels with `--link` over their accent fill, measured at 1.19:1 on the `/sample` banner button. The post-fix run came back with `/sample` still at 95 on a single node, which is how it was found; wrapping the theme selector in `:where()` restores specificity (0,0,1), identical to the original global `a` rule, and all five light routes then reached 100. It is recorded because it was caught by re-running before committing rather than after, and because a fix that reads as clean in the final diff was not clean in the making.

## Known issues

Open items. None of them affects the current scores on the five audited routes.

- `src/pages/Interview.css:315` and `:1054` set text on a brand-tinted surface using `--accent-hover` instead of `--brand-tint-text`. Since 2026-07-27 both tokens resolve to `#4852b8` in light, so these two call sites now look correct by coincidence rather than by construction. They will break silently if `--accent-hover` ever moves.
- `--text-muted` `#656d7a` measures only 4.74:1 on `--bg-secondary` `#f3f4f5`. The bottom of the light neutral scale is compressed against that surface, which is what caps the `--text-tertiary` window and leaves it clearing the real floor by 0.04. Darkening `--text-muted` would push that compression up toward `--text-secondary` rather than relieving it, so it is deliberately not done here.
- The landing mock score tile (`.landing-tile__value--high`) and the real Results score tiles now use different green tokens. The mock uses `--pill-success-text` because it sits on `--surface-inset`; the real tiles keep `--score-high` because they sit on white. A knowing divergence between a marketing mock and the page it mirrors.
- `.interview-topbar__mute--off` puts `--text-tertiary` on `#f3f4f5` when hovered, clearing 4.5:1 by 0.04. Accepted rather than lightening a hover background and losing an affordance signal.
- **The tracker keyboard remediation has never been exercised by an automated run.** The 2026-07-26 remediation entry for making expandable tracker rows keyboard-operable (`role="button"`, `tabIndex`, Enter/Space, `aria-expanded`, visible focus ring) is not covered by any archived Lighthouse run, because no archived run rendered a single tracker row. axe does check `aria-expanded`, `role` and `button-name`, so a populated run would exercise checks that an empty run structurally cannot reach. This is a different gap from the note in the 2026-07-26 remediation log that four of six entries lack before-side evidence: this entry additionally lacks automated **after**-side evidence, and rests on source review alone. The 2026-07-26 manual keyboard walkthrough could not reach an expandable tracker row either, for the same reason the automated runs could not: it was performed against `localhost:4173`, where the tracker is always empty. The same limit applies to any `/upload` behaviour that only appears once a file or job description is present.
- **Closing that gap has a privacy constraint.** A run captured from a populated or genuinely signed-in session must not be committed with `fullPageScreenshot` intact. Every Lighthouse JSON embeds a full-page image of the rendered route as base64 under the top-level `fullPageScreenshot` key, and `--output=json` has no flag to suppress it, so it would have to be stripped after the run. The existing captures are clean because the backend 401 stopped any data reaching the page, not because the capture method excluded it.

## Notes for testers

Screen-reader spot checks (VoiceOver/NVDA) are recommended as ongoing practice. Reduced motion is honored via `prefers-reduced-motion` in animated views.
